Observable · concepto

La respuesta que llega después

Describir lo que va a llegar y dejar instrucciones para cuando llegue, mientras el programa sigue con lo demás.

3.1 · Para qué existe

Casi todo lo que has programado hasta ahora pasa de inmediato: sumas dos números y el resultado está en la línea siguiente; filtras una lista y la lista filtrada ya existe. Pero hay cosas que tardan: una respuesta de un servidor, un archivo que se lee del disco, un temporizador. No sabes si va a tardar 50 milisegundos o 5 segundos, ni si va a llegar.

Si el programa se quedara quieto esperando, la pantalla se congelaría: no podrías escribir en el buscador ni hacer clic en nada. Lo que hace falta es una forma de describir “lo que va a llegar” y dejar instrucciones para cuando llegue, mientras el programa sigue con lo demás.

3.2 · Qué es

Definición técnica

Observable

Un Observable es un objeto que representa una fuente de valores que llegan con el tiempo (cero, uno o muchos) y que solo empieza a producirlos cuando alguien se suscribe con subscribe(). Quien se suscribe entrega funciones que el Observable llama en cada momento: next cuando llega un valor, error si algo falla y complete cuando ya no habrá más valores. Viene de la librería RxJS, que Angular instala con cada proyecto.

RxJS · Angular
Explicación sencilla

Es un pedido que dejas descrito, pero que nadie empieza a preparar hasta que dices “sí, lo quiero”. Cuando dices que sí, dejas dicho qué hacer cuando llegue, y sigues con lo tuyo.

En la vida real

El domicilio. Armar el pedido en la app no hace que la cocina prepare nada; tocar Pedir sí. Desde ese momento la app te avisa: “tu pedido llegó” (next), “el restaurante canceló” (error) o “pedido entregado, fin” (complete).

3.3 · Cómo funciona

Cuando escribes new Observable(receta), RxJS guarda la receta y no la ejecuta. El Observable es solo una descripción. Cuando llamas subscribe(observer), RxJS ejecuta la receta y le pasa un cliente conectado a tu observer: cada cliente.next(x) termina llamando a tu next(x).

Lo que tarda no bloquea: setTimeout deja la entrega programada y el programa sigue. HttpClient funciona igual: http.get(url) no envía la petición; devuelve un Observable cuya receta es “envía la petición”. La petición sale cuando alguien se suscribe, y cuando llega la respuesta el Observable llama next con los datos y después complete.

3.4 · Cómo reconocerlo

Hazte dos preguntas: ¿el valor que necesito existe ya, o va a llegar después? y ¿quiero poder describir el pedido ahora y decidir después cuándo hacerlo? Si el valor llega después (una respuesta de red, un temporizador, un clic que todavía no ha pasado), necesitas algo como un Observable. Y si ves .subscribe( en un código, ahí es donde el pedido realmente sale.

5.3 · Resolver CORS con el proxy

Tarima corre en http://localhost:4200 y el backend en http://localhost:8080. Para el navegador son orígenes distintos, y por seguridad no deja que el código de una página lea respuestas de otro origen, salvo que ese otro origen lo autorice con unas cabeceras especiales. Esa regla se llama CORS.

La solución de desarrollo es el proxy de ng serve: tu código pide a /api/eventos en el mismo origen, y el servidor de Angular reenvía esa petición a localhost:8080. Es como el portero del edificio que recibe el paquete por ti.

import { Evento } from '../../models/evento';
import { TarjetaEvento } from '../../components/tarjeta-evento/tarjeta-evento';
import { CarritoStore } from '../../services/carrito-store';

  selector: 'app-listado-eventos',
  styleUrl: './listado-eventos.css',
  templateUrl: './listado-eventos.html',
})
export class ListadoEventos {
  private readonly carrito = inject(CarritoStore);
  private readonly api = inject(EventosApi);

  eventos = signal<Evento[]>([]);
  categorias = ['Todas', 'Concierto', 'Teatro', 'Stand-up'];

  busqueda = signal('');
  categoria = signal('Todas');

  eventosFiltrados = computed(() => {
    const texto = this.busqueda().trim().toLowerCase();
    const categoria = this.categoria();

      (evento) =>
        evento.nombre.toLowerCase().includes(texto) &&
        (categoria === 'Todas' || evento.categoria === categoria),
    );
  });

  constructor() {
    this.api.listar().subscribe((eventos) => this.eventos.set(eventos));
  }

  agregarAlCarrito(evento: Evento): void {
    this.carrito.agregar(evento);
  }
}

Observable · límites

No todo necesita un Observable

7.1 · Cuándo no usarlo

No uses un Observable para algo que ya tienes. Si el valor existe en este instante (una lista en memoria, el texto del buscador, un total que se calcula), una variable, una signal o un computed son más simples y más claros.

En Angular, el lugar natural de los Observables es la frontera con lo que tarda: HttpClient, eventos del navegador, temporizadores. Dentro de la aplicación, el estado vive en signals, y las respuestas que llegan como Observable se guardan en signals con set.

7.3 · Errores frecuentes

Olvidar el subscribe

7.4 · En un sistema real

El proxy es solo para desarrollo. Al publicar, frontend y backend pueden estar bajo el mismo dominio o el backend puede configurar CORS. Por eso la URL del servicio es relativa: el mismo código funciona en los dos casos.

Tres situaciones muy distintas no pueden verse como el mismo hueco en pantalla.

8.1 · Para qué existe

Cuando un dato llega de afuera, la pantalla pasa por momentos distintos: primero no hay nada porque la respuesta no ha llegado; después llega bien o llega un error. Si el código solo contempla el caso feliz, los otros se ven como si fueran ese caso: un “cargando” se ve como “no hay nada”, y un servidor caído también.

Hay un problema peor: si solo se contempla el caso feliz y la respuesta falla, el programa se encuentra con un error que nadie atiende. En el mejor caso no pasa nada visible; en el peor, el programa se detiene.

8.2 · Qué es

Definición técnica

Estados de una petición

Las situaciones en que puede estar una vista que depende de datos remotos: cargando (la petición salió y no ha respondido), error (respondió con un fallo o no pudo conectar), vacío (respondió bien, pero sin datos que mostrar) y éxito (respondió con datos). En código, cada estado se representa con un dato que se actualiza en next y en error.

Explicación sencilla

Antes de mostrar los datos, la pantalla se pregunta “¿ya llegó?”, “¿llegó bien?” y “¿llegó algo?”, y para cada respuesta tiene un mensaje.

En la vida real

El tablero de un aeropuerto. Un vuelo dice “Programado”, “Embarcando”, “Demorado” o “Cancelado”. Nadie ve una fila vacía y adivina.

11.1 · Cuándo no usarlo

Los estados de carga y error son para datos que llegan de afuera. Un valor calculado en memoria, una lista que ya llegó y se filtra, o un dato que el usuario acaba de escribir no tienen “cargando” ni “error de red”. Agregarlos complica la plantilla y enseña a la persona a desconfiar de pantallas que sí son confiables.

11.3 · Variantes y casos límite

El 404 depende de la pantalla. En el detalle, un 404 es “ese evento no existe”. En la cartelera, un 404 de /api/eventos significaría que la dirección está mal: ahí sí es un error.

El 0 y el 502 dicen cosas distintas. Con el proxy, si el backend está apagado responde el proxy con 502. Si no hay red o el navegador bloqueó la petición, no hay respuesta y el código es 0.

POST · concepto

Entregar datos y recibir el comprobante

GET pregunta; POST entrega un sobre con datos y espera el recibo.

12.1 · Para qué existe

Con GET el navegador pide algo que ya existe en el servidor. Pero muchas acciones consisten en crear algo nuevo: una reserva, un pedido, un comentario, un registro. Ese algo nuevo no está en el servidor; lo tiene el navegador, en lo que la persona escribió.

Hace falta una forma de decirle al servidor “toma estos datos y guárdalos”, llevando los datos dentro de la petición, y de saber después si de verdad quedaron guardados.

12.2 · Qué es

Definición técnica

POST

POST es el método HTTP para enviar datos al servidor con el fin de que cree un recurso o procese una acción. Los datos viajan en el cuerpo de la petición, normalmente como JSON, con la cabecera Content-Type: application/json. Si creó el recurso, responde 201 Created; si los datos no sirven, responde 400 Bad Request.

Explicación sencilla

GET es preguntar; POST es entregar un sobre con datos y esperar el recibo.

En la vida real

Radicar una carta: entregas el sobre, en la ventanilla le ponen un sello con número de radicado y, si falta la firma, te lo devuelven sin radicar.

import { Service, computed, signal } from '@angular/core';
import { Evento } from '../models/evento';
import { ItemCarrito } from '../models/item-carrito';

@Service()
export class CarritoStore {
  private readonly items = signal<ItemCarrito[]>([]);

  readonly entradas = this.items.asReadonly();

  readonly totalEntradas = computed(() => {
    let total = 0;
    for (const item of this.items()) {
      total += item.cantidad;
    }
    return total;
  });

  readonly totalAPagar = computed(() => {
    let total = 0;
    for (const item of this.items()) {
      total += item.cantidad * item.evento.precio;
    }
    return total;
  });

  agregar(evento: Evento): void {
    this.items.update((items) => {
      const yaEsta = items.some((item) => item.evento.id === evento.id);
      if (!yaEsta) {
        return [...items, { evento, cantidad: 1 }];
      }
      return items.map((item) =>
        item.evento.id === evento.id ? { ...item, cantidad: item.cantidad + 1 } : item,
      );
    });
  }

  quitar(id: number): void {
    this.items.update((items) => items.filter((item) => item.evento.id !== id));
  }

  vaciar(): void {
    this.items.set([]);
  }
}

POST · límites

Crear no es consultar

El método expresa la intención, y repetir una creación sí cambia el sistema.

15.1 · Cuándo no usarlo

No uses POST para consultar. POST le dice al servidor “esto cambia algo”, y por eso el navegador no lo repite solo ni lo guarda en caché, y el usuario no lo puede compartir como enlace. Para pedir datos, GET; para crear, POST. Para modificar o borrar existen PUT, PATCH y DELETE, que llegan con el backend propio del Módulo 2.

15.2 · Con qué se confunde

Donde chocan es en la repetición. Recargar una página que hizo GET es inofensivo; reenviar un POST crea otra reserva. Por eso el botón se deshabilita mientras enviando() es verdadero.

15.3 · Errores frecuentes

Olvidar el subscribe

El botón queda en “Reservando…” y la pestaña Red no muestra nada. El Observable de post es frío, igual que el de get.

Enviar otros nombres

Si el cuerpo dice nombre en vez de nombreCompleto, el backend responde 400. La interfaz Reserva evita el error.

Mandar datos que decide el backend

Precio y total no viajan desde el navegador: alguien podría modificarlos. La persona decide qué y cuántas; el backend calcula lo demás.

Vaciar antes de la respuesta

vaciar() va dentro de next. Si va después del subscribe, el carrito se borra aunque la reserva falle.

15.4 · En un sistema real

El 400 de Tarima dice “Ocurrió un error (código 400).”, pero el backend sí explicó el motivo con { "mensaje": "Cupos insuficientes" }, disponible en error.error. En producción, frontend y backend acuerdan un formato de error; el frontend valida antes de enviar y el backend vuelve a validar todo, porque no puede confiar en el navegador.

Conexión

Con GET Tarima pregunta; con POST, cuenta. Los dos devuelven un Observable frío y necesitan estados: el “cargando” de la cartelera es el “enviando” de la reserva. Solo queda que el inicio deje de usar el mock.

Adiós a los datos de prueba

Las páginas muestran; el servicio de API habla con el backend.

La regla de la Fase 4 de Huella Amiga, y la de cualquier proyecto con backend, es que ninguna página ni componente importa los datos de prueba ni HttpClient: los datos llegan por el servicio de API. Es el principio de responsabilidad única (la S de SOLID): cada pieza tiene una sola razón para cambiar. Si la URL del backend cambia, cambia EventosApi; si cambia la forma de mostrar los destacados, cambia Inicio. Ninguna de las dos se entera de lo que le pasa a la otra.

  1. Un Observable describe algo que llega después y no hace nada hasta que alguien se suscribe. HttpClient devuelve Observables: sin subscribe, no sale ninguna petición.
  2. Toda pantalla que depende de algo externo tiene estados: cargando, error, vacío y éxito. Cada camino (next y error) apaga la carga, y la persona ve un mensaje que entiende.
  3. GET pregunta y POST crea: el POST lleva datos en el cuerpo, el servidor confirma con 201 y devuelve lo creado. Repetirlo crea otra vez, por eso el botón se bloquea mientras envía.
La decisión técnica del día

Las páginas no saben dónde están los datos. Todo lo que habla con el backend vive en EventosApi, con direcciones relativas (/api/...) que pasan por el proxy. Si mañana el backend cambia de dirección, cambia un archivo, y el mismo código funciona en desarrollo y publicado.
